# Partial invoicing: integration contract

Status: **not activated**. Current application still creates one invoice after full shipment. Stage5 must be integrated after incoming-QC/ledger hardening. The delivered `allocateInvoicePortion` calculation has5 passing tests; it does not issue invoices or grant return eligibility.

## Central schema migration

1. Remove only the unique constraint on `invoices.order_id`, retain its FK and add a nonunique lookup index. Keep invoice IDs/numbers, amounts, payments and issued document snapshots unchanged.
2. Add `invoice_items`: UUID PK, invoice_id FK, sale_item_id FK, positive integer quantity, subtotal/tax/total numeric(18,2), nonnegative money checks and total=subtotal+tax, immutable JSON snapshot. Unique(invoice_id,sale_item_id). Snapshot includes existing product/variant/SKU description, original ordered quantity, unit price, discount, whole-line branding total, whole-line agreed subtotal, allocated line subtotal/tax/total, currency, and frozen tax rate.
3. Add `invoice_shipment_allocations`: UUID PK, invoice_item_id FK, shipment_item_id FK, positive integer quantity, unique(invoice_item_id,shipment_item_id). Index shipment_item_id for cumulative capacity checks. A deferred guard locks the parent sales order and verifies invoice and shipment refer to the same sale line/order, item quantity equals allocation sum, invoice header totals equal item sums, cumulative shipment allocations<=shipment quantity, cumulative sale-line invoice quantities<=ordered quantity.
4. New invoice tax rate must match prior issued invoices for its order. Freeze tax rate at first issuance, enforced under the sales order lock and a database guard; later invoices cannot silently select another rate.
5. Add UPDATE/DELETE immutability guards to items and allocations; headers/financial records retain existing protections. Corrections use explicit credit documents, not invoice deletion.

Migration preflight checks existing invoice amounts against historical agreed sale lines, shipment quantities and fixed tax. Backfill legacy invoice items/allocations only where whole-order correspondence is provable. Allocate them using the same cumulative calculation. If evidence does not reconcile, abort the backfill and report record counts for manual review; never invent line prices or rewrite legacy totals. Issued PDF snapshots remain authoritative and unchanged. Apply on isolated Neon first, never regenerate earlier migration snapshots.

## Issuance service and operation interface

Existing invoice payload extends `{id: salesOrderId, dueDate, taxRate}` with optional `lines: [{shipmentItemId, quantity}]`. Omitted lines select all currently dispatched, not-yet-invoiced quantities. Empty selection fails; duplicate shipment IDs fail; quantities are positive integers. A default full invoice therefore retains old form behavior but also works after partial shipment.

Within existing `execute` transaction/idempotency wrapper: lock sales order first; validate state includes Partially Shipped/Shipped/Completed and actual shipment evidence exists; lock/read allocations; cap selected quantities against remaining dispatched amounts; reject overinvoice; derive quantities by sale line. Read *all* frozen sales lines, their prior billed quantities, and selected quantities into `allocateInvoicePortion`. Capture complete immutable snapshots and issue header+items+shipment allocations atomically. Pass the created invoice ID directly to document capture; never select the first invoice by order ID. Retry same key returns original outcome, retry fresh key against already allocated units fails.

`allocateInvoicePortion` sorts complete order lines by ID, checks their subtotal sum equals stored order subtotal, allocates whole-order rounded tax by cumulative line-value proportions, then allocates each line's subtotal and tax independently by cumulative billed units. Independently prorating tax avoids negative tax-cent lines. Merchandise discounts and frozen branding/setup charges are part of the original line subtotal; setup is not charged again for every invoice. All calculations use Decimal precision40 and HALF_UP with two-decimal money, no floating-point money conversion. Every call includes lines billed previously or not selected now, so denominator/tax allocation cannot change. Zero-priced orders issue zero-valued paid invoices. Same currency only, no implicit FX.

## Required integrations before enabling

- **Payments/fulfillment:** paying one partial invoice must not mark the whole order Completed. Recompute order completion only when fully shipped, fully invoiced and all invoice positions settled after credits/refunds. Use all invoices for order-level balances.
- **Returns:** require selected delivered shipment quantities to be allocated to the chosen invoice, cap claims by both delivered quantity and invoice allocation. Preserve global physical-return cap across invoices/RMAs. `returnCreditAmount` must use that invoice item's original subtotal/tax and invoiced quantity, sum prior credits restricted to *invoice+sale line*, not every credit for the sale line. Each RMA still references one original invoice; split separate RMAs where goods span invoices. Zero-valued/exchange paths remain normal physical workflows.
- **Documents:** new invoice rendering uses invoice_items, never all sales lines. Preserve issued snapshots and line taxation. Include shipment/invoice references in RMA/credit documents. Capture only newly created invoice ID.
- **UI/queries/CSV:** replace first-invoice lookups with lists on sales/customer/shipment pages; select shipment quantities on creation form; show dispatched/unbilled, invoiced/paid/outstanding; keep role guards. Invoice detail remains `/invoices/[id]`. Invoice reports aggregate all headers by currency without double-counting sale totals.
- **Constraints/history:** existing generic history triggers and all queries assuming one invoice/order must be reviewed before dropping uniqueness. No activation by exposing a new button alone.

## Required verification

Regression paths: two shipments→two invoices→independent partial payments→order completion; concurrent attempts same shipment; same/new operation-key retry; multi-line tax/setup rounding sum equals original whole order; fully discounted/no-charge invoice; return delivered invoiced portion before rest order shipped; overreturn after prior RMA/credits; credit/refund amounts bounded to exact invoice; legacy invoice backfill; unchanged issued snapshots; invoice permissions and server-calculated amounts. Real Neon branch verification must reconnect and requery snapshots/allocations after each operation. Existing full-order workflow must still pass. No production synthetic business records.
